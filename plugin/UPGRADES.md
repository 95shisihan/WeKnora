# 插件升级

系统管理员在「设置 → 插件管理」的每个外部插件卡片上点击「升级插件」，直接上传编译 ZIP。内置插件随宿主更新，不提供单独上传入口。

1. 等待该插件的同步或连接验证结束，关闭启用开关。
2. 点击「升级插件」，选择不超过 64 MiB 的新版 ZIP，并确认目标插件及文件。
3. 宿主检查相同插件 ID、严格递增的语义版本、相同扩展 ID / 类型 / 协议 / 认证方式以及相同配置 schema。破坏性配置迁移目前不支持，会拒绝升级；插件作者仍须保证旧凭据、资源 ID 和增量游标可读。
4. 宿主备份旧包，替换安装目录，在数据库事务中迁移默认数据源名称。只匹配同一连接器类型且名称完全等于旧默认名称的非删除记录，跨租户生效。扩展点 name 优先于插件 metadata.name。自定义名称保留；历史记录没有命名来源标记，因此手动输入恰好等于默认名称也会跟随升级。
5. 数据源 ID、配置、文档、同步游标和记录均保留。升级后插件停用；管理员重新启用，受控 HTTP 需要批准新版本权限。

接口：`POST /api/v1/system/admin/plugins/:plugin_id/upgrade`，multipart 字段 `file`。返回 `plugin` 状态及 `renamed_data_sources` 数量。普通安装接口继续拒绝重复 ID。升级接口只接受已停用插件。

备份位于安装目录父级的 `.upgrade-backups/<插件ID>-<随机值>/package`，不会被插件发现流程加载。正常替换或数据库迁移报错时自动恢复旧包；升级后的运行错误不会自动降级。此机制不提供跨文件系统与数据库的断电原子事务。若进程在替换中异常退出，应检查备份、当前 plugin.yaml 及数据库名称后恢复；旧包备份不会自动清理。

验证覆盖：错误 ID、重复/回退版本、扩展或 schema 变化、运行中升级拒绝、迁移失败恢复、备份不被扫描、默认/自定义名称、跨租户名称迁移以及凭据和游标保持不变。
